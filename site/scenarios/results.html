Run manifest and metrics contract (run-manifest/v1)

The machine-checkable form of the evidence contract below (issue #60): a manifest validator with typed diagnostics, ten metric definitions that each state their clock and what they do not show, and a summary generator that refuses any input not marked synthetic. Module: examples/run-manifest/.

python3 examples/run-manifest/rm_validate.py examples/run-manifest/fixtures/manifests/valid/*.json
python3 examples/run-manifest/rm_summary.py --check
python3 -m unittest discover -s examples/run-manifest/tests -t examples/run-manifest

What this does not show: every manifest, run file, table and plot in it is invented by a seeded generator. A manifest that validates is well-formed, not true. Real benchmarking stays gated on the cross-worker baseline (#14, #15, #16).

Pod recovery definitions (DataAnalysis/)

Distinct, named measurements after one pod is deleted (issue #45, merged in #131): deletion request to replacement pod observed, and replacement observed to Ready, both on the local monotonic clock; auxiliary Kubernetes-timestamp intervals; and disruption to first restored ROS message, which stays not_measured unless a probe record is supplied. Details: DataAnalysis/README.md.

python3 DataAnalysis/recovery_metrics.py analyze \
  --observation DataAnalysis/fixtures_recovery/success_basic.json
# exits 1 by design: the fixture has no replacement pod
python3 DataAnalysis/recovery_metrics.py analyze \
  --observation DataAnalysis/fixtures_recovery/fail_no_replacement.json --format json

What this does not show: the fixtures are synthetic, and a Ready pod is Kubernetes readiness, not ROS application recovery. The live collector (a dry run unless --yes) has not been run on a real cluster, and no producer of the ROS message probe exists yet. Historical recovery numbers must not be reinterpreted with these definitions.

Every command above was run on 2026-11-20 at commit e45de7a with Python 3.12.3; each exited 0 except the one marked to exit 1, which did. The scenario pages carry a longer “Run it offline” block for each track.

03 / Evidence contract

What a result submission must contain.

01 / INPUTS

Frozen experiment

Task and null hypothesis, exact dataset/split and license, source and container commits, model/revision and question criteria hash, hardware/clock and network profile.

02 / RUNS

Raw and failed outcomes

Run IDs, seeds, repeats, all valid/invalid/unknown predictions, provider outages, latency with units, actual measurement source and cost assumptions.

03 / REPRODUCTION

Independent review

Raw shareable files, SHA-256 hashes, scripts and exact replay commands, calculated uncertainty and limitations, human-reviewed evidence URL.

Status rules

  • Planned: question and methodology exist; measured values must remain null.
  • Collecting: trial evidence is under review; measured values remain undisplayed.
  • Verified: public evidence, immutable run manifest hash and numerical metric exist and were independently reviewed.

Research safeguards

Use synthetic or licensed data; never commit secret tokens, private ROS telemetry, real robot addresses or unapproved human recordings. Independent deterministic safety controls and simulator-only boundaries are mandatory. Neither TypeSafe nor this website certifies a robot controller.

04 / Contribute results

Publishing a negative finding is valuable too.

Propose a reproducible experiment

Before submitting claims, read the scenario, preregister metrics and create a small issue/PR that includes scripts, synthetic or licensed raw data, failures, and an evidence manifest. See the dedicated results issue and Claude Code/Codex instructions.
